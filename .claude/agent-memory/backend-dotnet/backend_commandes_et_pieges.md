## Conventions
- Solution `chantier-backend/Chantier.sln` : `Core/Chantier.Core` (sans EF ni ASP.NET), `Core/Chantier.Infrastructure`, `WebApi/Chantier.WebApi`, `Tests/Chantier.UnitTests`, `Tests/Chantier.IntegrationTests`. Namespaces file-scoped, `TreatWarningsAsErrors`, paquets centralisés (`Directory.Packages.props`).
- Un cas métier attendu = exception typée de `Core/Exceptions` (code stable de `ErrorCodes`) ; `GlobalExceptionMiddleware.Map` fait exception -> statut + `code`. Toute réponse d'erreur passe par `ProblemResponses` (type, title, status, detail, code, traceId). Nouveau code = `ErrorCodes` + `ErrorCatalog` + `docs/api/codes-erreur.md` (test `ErrorCatalogTests`).
- Lecture par `Specification` Ardalis ; mapping manuel `XxxResponse.From(...)` ; DTO d'entrée sans champ protégé (test d'architecture `ControllerArchitectureTests`, types `*Request` seulement ; les corps d'action s'appellent `*Body`).
- `[SiteScoped]` est un filtre de RESSOURCE (avant la liaison du corps) : un corps invalide ne révèle pas l'existence d'un chantier non affecté. Obligatoire sur toute route `{siteId:guid}` ; les routes sans chantier du lot matériaux sont dans une liste blanche du test d'architecture.
- Audit uniquement par `AuditingInterceptor` (setters privés, `MarkCreated/Updated/Deleted`, UN seul `now` par `SaveChanges`). `DbSet.Remove` devient une suppression logique. Écritures hors requête (seeders) = auteur `SystemActor`.
- Idempotence : vérifier le `clientId` AVANT et APRÈS la vérification de position (course entre renvois parallèles), cf. `ZoneService.ResolveRaceAsync` et `RequestService.CreateAsync`.
- Synchronisation : une `ISyncSource` par entité lue, un `ISyncPushHandler` par entité écrite ; toute entité `ISiteScoped` s'ajoute à `SyncTouch.TouchedEntityTypes` (test d'architecture) et `TouchLinesAsync` les touche TOUTES seul (tables tirées du modèle EF, `READPAST`). Entités globales (`product`, `supplier`) : `SyncChangeRow.SiteId` nul, source qui ignore le filtre de chantier. Numérotation : `ISiteNumbering.NextAsync` dans la transaction de l'entité, idempotence (`clientId`) vérifiée d'abord.
- **Une seule source de règles** : `RequestService` sert l'API REST ET la synchronisation (`RequestSyncPushHandler` ne fait que traduire : `ConflictException` / codes `DEMANDE_VERROUILLEE`, `TRANSITION_INTERDITE`, `DEMANDE_NON_OUVERTE` = `conflict` avec l'état courant en forme de synchro, autre `DomainException` = `rejected`). Ordre dans une modification : droit -> verrou de statut (`EnsureEditable`, avant toute validation de contenu) -> comparaison à trois valeurs (`FieldMergeEvaluator` + `RequestCanonical`) -> validation -> écriture.
- Journal d'opérations (`SyncOperationLog`) : écrit dans la transaction de l'opération pour `update` et `transition` seulement (un `create` est idempotent par son index unique) ; renvoi = relecture du journal ; `UserId` différent = refus neutre.
- Écritures d'une demande : `DbTransactions.RunAsync` (crée ou REJOINT la transaction) + `AppLocks.AcquireAsync("material-request:<id>")` avant de charger la demande. Noms et ordre des verrous : `MaterialLocks` (livraison PUIS demande, toujours avant la 1re écriture) ; `MaterialLocks.RetryAsync` rejoue le corps si `DbUpdateConcurrencyException`.
- **Recalcul** : `IRequestRecalculator` (seul écrivain de `ReceivedQuantity`, statut après `Ordered`, `IsSettled`, `Delivery.QuantityInRequestUnit/Amount`) ; appelé après chaque écriture de livraison/commande, dans la transaction. `IRequestEventWriter.Add` ajoute l'événement ET marque `UpdatedAt` modifié sur le sujet (version avance : la synchro envoie la ligne avec son historique). `CommercialProjection` = seul constructeur de `commercial`. Livraison = fait de chantier : jamais refusée, non rattachée avec `UnattachedReason`.
- Projecteurs : `RequestProjector` (`includeCommercial`, `includeDeliveries`), `DeliveryProjector` (`includeCommercial`, `includePhotos`) ; la synchro passe `false` partout et applique `RequestSyncData.From` / `DeliverySyncData.From`.
- Photos : `IPhotoStorage` (`FileSystemPhotoStorage`, racine `Storage:PhotosRoot`, `.staging` puis déplacement, clé `<site>/<AAAA>/<MM>/<guid>.jpg` validée par regex), `JpegMetadataStripper` (APP1/APP13 retirés, sans réencodage), `MeteredStream` (limite + SHA-256 au fil du flux). Exceptions `FileTooLargeException` (413) et `UnsupportedFileTypeException` (415) ; JPEG incohérent ou empreinte fausse = 422 `TYPE_FICHIER_REFUSE`.

## Commandes qui marchent
- Build et tests : `cd chantier-backend; dotnet build; dotnet test`. Sans variable, les tests d'intégration lancent un conteneur Testcontainers (Docker, ~50 s).
- Réutiliser le conteneur de dev sans afficher le mot de passe : `set -a; . /d/projects/Chantier/.env; set +a; export CHANTIER_TEST_SQL="Server=127.0.0.1,14335;User Id=sa;Password=${MSSQL_SA_PASSWORD};TrustServerCertificate=True;Encrypt=False"` (le fixture crée puis supprime des bases `chantier_test_*`). Suite complète : environ 2 min 30.
- OpenAPI : `dotnet build` écrit `docs/api/openapi.json` (test `OpenApiContractTests` = fichier commité identique au code). Désactiver : `-p:OpenApiGenerateDocuments=false`.
- Migration : `dotnet ef migrations add <Nom> --project Core/Chantier.Infrastructure --startup-project WebApi/Chantier.WebApi -o Persistence/Migrations` (exporter `ConnectionStrings__ChantierDb` factice ; pas de connexion nécessaire) ; `dotnet ef migrations script <de> <vers> --idempotent` pour relire le SQL.
- Secrets de dev : `dotnet user-secrets set` dans `WebApi/Chantier.WebApi` (id `chantier-webapi`). Ils ne sont chargés qu'en Development.
- API locale avec démo : `ASPNETCORE_ENVIRONMENT=Development Seed__Demo=true dotnet run --no-build --no-launch-profile --urls http://localhost:8195`.
- Format : `dotnet format Chantier.sln` puis `--verify-no-changes` (règle IMPORTS : `using System.*` d'abord, puis les autres par ordre alphabétique).
- Build bloqué (MSB3021, DLL verrouillées) : l'API de dev tourne (`.dev/api.pid`) ; arrêter AUSSI le parent `dotnet run`, sinon elle est relancée ; elle peut être relancée par quelqu'un d'autre en cours de tâche : revérifier `Get-Process Chantier.WebApi` avant un build.
- Vérifier une migration sur vraie base : base temporaire dans `chantier-dev-db`, `dotnet ef database update <migration précédente>`, insérer des lignes par `sqlcmd -I`, puis `database update`.
- Interblocages SQL : `docker exec chantier-dev-db bash -c '/opt/mssql-tools18/bin/sqlcmd -C -S localhost -U sa -P "$MSSQL_SA_PASSWORD" -Q "DBCC TRACEON(1222,-1)"'` (préfixer `MSYS_NO_PATHCONV=1` sous Git Bash), relancer le test, puis `EXEC sp_readerrorlog 0,1,N'deadlock-list'` ; penser à `DBCC TRACEOFF(1222,-1)`.
- Générateurs de clients (vérifiés B6 du socle) : web `@rtk-query/codegen-openapi` ; mobile `swagger_parser 1.46.0` (PAS 2.x) avec `use_freezed3: true`, `retrofit 4.4.2` + `retrofit_generator 9.1.9`.

## Pièges connus
- **L'API de dev redémarrée (`dotnet run`) compile puis applique tout de suite les migrations présentes** à `ChantierDev` : ne jamais modifier une migration générée avant d'être sûr qu'elle n'a pas été appliquée (`__EFMigrationsHistory`) ; `AddMaterialRequests` l'a été, d'où une seconde migration pour la colonne ajoutée.
- Horloge de test : la validation JWT utilise l'horloge RÉELLE. Ne jamais `FakeTimeProvider.SetUtcNow` en arrière (exception) ni à une date fixe ; seulement `Advance`, après les connexions. Avec `FakeTimeProvider` toutes les lignes ont le même `CreatedAt`.
- `Guid.CreateVersion7()` n'est PAS monotone dans la même milliseconde, EF insère par ordre de clé et un `ORDER BY` SQL sur un `uniqueidentifier` ne suit pas l'ordre C# : l'historique utilise `MonotonicGuid` (événements) et un tri par `RowVersion`.
- **Interblocage 1205 entre deux écritures de la même demande** : l'ordre des verrous (événement avant demande, ou relecture de l'historique après l'écriture) diffère ; solution : transaction + `sp_getapplock` par demande avant de la charger (`AppLocks`). Un test de concurrence ne révèle le défaut que si les requêtes se chevauchent : lancer la classe en boucle.
- Les produits et fournisseurs sont GLOBAUX : ils apparaissent dans tous les pulls. Les fixtures de tests matériaux créent leur PROPRE base (`SqlServerFixture.CreateDatabaseAsync`) pour ne pas changer les assertions des tests de synchronisation du socle (qui comptent les lignes).
- Une requête sur la table pendant qu'une transaction ouverte verrouille une ligne se bloque : dans les tests de curseur, filtrer par fenêtre de version, pas par Id.
- `[AllowAnonymous]` au niveau classe écrase les `[Authorize]` des actions (erreur ASP0026) : le placer sur les actions.
- Écrire des fichiers avec Python sous Windows donne du CRLF : utiliser `newline=''`. Les heredocs Bash avec apostrophes ou `\` échouent ou mangent les caractères : écrire le script Python avec l'outil Write puis l'exécuter (même chose pour les chemins Windows dans un `.csproj`).
- `MsSqlBuilder()` sans image est obsolète. NUnit : `TestDelegate` obsolète (utiliser `Action`), analyseur NUnit1032 pour les fabriques à libérer.
- Les messages d'exception inattendus (500) sont journalisés avec leur pile : aucune donnée personnelle (téléphone fournisseur) dans un message d'exception ni un message de validation.
- `ExecuteUpdateAsync(SetProperty(x => x.UpdatedAt, x => x.UpdatedAt))` fait bien avancer le `rowversion` sans toucher à l'audit.
- Génération OpenAPI au build : l'hôte démarre vraiment ; commentaires XML multi-lignes en CRLF normalisés par le transformateur ; un type avec convertisseur JSON personnalisé (`DateOnly` strict) perd son `type` dans le schéma. `CS1573` désactivé dans Core ; pas de `<see cref>` ni `<b>` dans les commentaires qui atteignent l'OpenAPI ; `<paramref>` d'un paramètre inexistant = erreur CS1734.
- Records avec membres `required` : un constructeur de copie dérivé exige `[SetsRequiredMembers]` et une propriété `required` ajoutée au dérivé casse (CS8618) ; utiliser une valeur par défaut. `SqlQueryRaw` avec une chaîne interpolée = EF1002 : construire la chaîne dans une variable locale (noms de tables du modèle EF seulement).
- **Numérotation** : les 5 compteurs naissent avec le chantier + migration `BackfillSiteCounters`. Repli : `sp_getapplock` puis `INSERT … WHERE NOT EXISTS` DANS la transaction de l'appelant. Ne PAS revenir à une seconde connexion ni à `HOLDLOCK`.
- **Limiteur de débit** : placé AVANT `UseAuthorization`, précédé de `RateLimitIdentityMiddleware` ; `AddWebApi(configuration)` lit le certificat des clés au moment de l'enregistrement (tests : variables d'environnement).
- **Session web** : cookie avec `session_stamp` et `login_at` ; la déconnexion web change le stamp. Tests de temps : fabrique dédiée.
- `TestServer` n'applique pas `MaxRequestBodySize` de Kestrel : le 413 se vérifie sur un vrai serveur.
- Recherche `q` : le nom libre et la remarque sont comparés avec la collation de la base (insensible à la casse, SENSIBLE aux accents) ; seul le catalogue a un nom normalisé.

- **Plusieurs agents relancent l'API de dev pendant une tâche** (web, mobile) : avant CHAQUE build, `Get-CimInstance Win32_Process` sur `Chantier.WebApi`, tuer l'exe ET son parent `dotnet run`. L'API relancée applique aussitôt les migrations présentes : ne plus modifier une migration générée.
- `GlobalExceptionMiddleware`/`SecurityHeadersMiddleware` : `Cache-Control: no-store` n'est posé que si la route n'a pas posé le sien (photo : `private, max-age=3600`).
- Un test qui force un statut en base (`SetStatusAsync`) ne passe plus pour `PartiallyDelivered` + solder : `SeedDeliveryRowAsync` ajoute une vraie livraison (numéro unique aléatoire).
- Les tests de photos partagent une racine temporaire par fabrique : comparer des listes de fichiers avant/après, jamais un total.
- Heredocs Bash avec apostrophes : toujours l'outil Write (échec silencieux sinon).

- **Démo matériaux** : `MaterialsDemoSeeder` écrit les entités directement (`MaterialRequest.Create/Approve/PlaceOrder/Receive`, `Delivery.Create`, `ISiteNumbering`, `IRequestEventWriter`, `IRequestRecalculator` avec `RequestActionContext(System)`), une transaction + `AppLocks` par chantier ; ne s'écrit que sur un chantier SANS demande/commande/livraison (corbeille comprise). La base de dev `ChantierDev` contient des données e2e du web et du mobile : la démo n'y charge que le catalogue et les logements ; pour le jeu complet : `scripts/dev.ps1 -Reset`.
- Générateurs (B11) : web `npm run generate:api` reproduit le fichier de travail ; mobile `dart run swagger_parser` + `dart run build_runner build --delete-conflicting-outputs` + `dart format lib`. Pour VÉRIFIER sans toucher : copier `lib/core/api` (et `libs/api-core/src/generated/chantierApi.ts`) dans le scratchpad, générer, comparer, restaurer. `Quantity` du contrat (corrigé après B11, écart 25) : `required [value, unit]`, référencée partout (y compris `*SyncData`, `oneOf [null, Quantity]` si facultative), jamais en ligne.

## Décisions (lien ADR)
- Convertisseur `RowVersion` gros-boutiste et `MIN_ACTIVE_ROWVERSION()` : ADR 0003. Limitation `auth` dans l'action : ADR 0005. Cursor des zones = décalage opaque.
- OpenAPI 3.1 conservé. Production : proxy inverse, certificat des clés (`docs/exploitation/production-backend.md`).
- Demandes de matériaux : ADR 0011 (modifications à trois valeurs, première arrivée retenue, journal), 0012 (aucun prix ni téléphone fournisseur en synchro, entités globales), 0014 (calculs et vecteurs partagés). Photos : ADR 0013. B11 : démonstration par amorçage direct (SystemActor, décision de l'orchestrateur), écarts 11 à 24 du contrat.

- **Schémas ajoutés à la main** (`AddSchemaAsync` du `ChantierDocumentTransformer`) : tout type imbriqué y est recopié EN LIGNE (enums, `product`, `history`, `variance`... hors `Quantity`, corrigée par `ReferenceSharedQuantity`, par réflexion sur le type C#). Un `required` posé dans `ChantierSchemaTransformer` sur un struct (`Quantity`) n'est pas pris en compte : le poser dans le transformateur de document.
- **Corrections R2 (2026-11-25)** : base en `READ_COMMITTED_SNAPSHOT` (migration `EnableReadCommittedSnapshot`, `suppressTransaction`, exige aucune autre connexion) ; `DbTransactions.RunAsync` rejoue 4 fois sur SQL 1205 (transaction créée par lui seulement, contexte vidé) ; `SqlErrors.IsTransient/Find` ; push : `retry` (`ERREUR_TEMPORAIRE`) ou `rejected ERREUR_INTERNE` par opération, jamais le lot perdu ; HTTP 503 + `Retry-After`. READPAST dans `SyncTouch` fonctionne sous RCSI (suite verte).
- **Synchro allégée** : `history` toujours `[]` dans `RequestSyncData`/`DeliverySyncData` (les projecteurs ne lisent plus les événements : `includeHistory:false`) ; `SyncWindow` (60 j, `Sync:ClosedRetentionDays`) filtre pull ET `SyncTouch` (SQL à part, mêmes règles) ; les tests lisent l'historique par REST.
- **Photos** : `PhotoCount` = fichiers reçus ; quota = reçues + `Pending` < 24 h ; `PhotoAdded` écrit à l'upload ; relire après verrou exige `ChangeTracker.Clear()` ; `JpegMetadataStripper` = liste blanche + coupe au 1er FFD9 (lit tout pour le SHA) ; `PhotoMaintenance` + worker (`Storage:Maintenance*`), validateur de `PhotosRoot` en Production (génération OpenAPI : `OpenApiGeneration.Settings()` fournit une racine absolue).
- **Boucle 1/2** : `Money.EnsureStorable` (quantité convertie / montant hors colonnes = 422 `QUANTITE_INVALIDE`, appelé dans `DeliveryService` ET `RequestRecalculator`) ; push : `SyncDependencies.KeysOf` + `blocked` dans `SyncPushService` (après un `retry`, toute opération qui partage une clé est `retry` sans handler) ; pull : `ResetRequired` = `SyncWindow.HasHiddenChangesAsync` (lignes visibles changées depuis le curseur et aujourd'hui hors fenêtre ; sans état, le client l'ignore pendant son rechargement) ; `DatabaseInitializer.WarnIfRowVersioningIsOffAsync`.
- Scripts de session : le build exige l'API de dev arrêtée à CHAQUE fois (d'autres agents la relancent) ; `Get-CimInstance Win32_Process` + tuer `Chantier.WebApi.exe` et son parent `dotnet`. Un script PowerShell qui édite un fichier avec `[IO.File]` doit recevoir un chemin ABSOLU (le répertoire courant .NET diffère) ; `` `r `` dans une chaîne PowerShell entre guillemets = retour chariot (casse « `retry` »).
- **Pull** : `SyncPullService` ordonne par version ; dans une page `changes` est rangé par rang parent (`ParentRank`) puis version, le curseur reste la version max. AUCUN ordre parent-enfant entre pages (écart 26) : traitement côté mobile.
